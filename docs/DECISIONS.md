# DECISIONS.md — 重要决策与替代方案

只记录**会影响后续长期实现**的决策：背景、选项、结论、被否方案、后果。
流水账式版本变化不进这里（见 `CHANGELOG.md`，待建）。

状态：`Active`（仍然有效）/ `Superseded`（被后续决策替代）/ `Open`（未定）。

---

## D-01 播放引擎：独立 mpv 进程 + 命名管道 IPC

- **状态**：Active
- **背景**：需要真正的 Hi-Res 解码、无缝续播、独占设备能力；Electron 的 `<audio>` 做不到。
- **选项**：① 渲染进程 `<audio>`；② 主进程原生音频模块；③ 独立 mpv 进程。
- **结论**：③。Node 侧监督 mpv，Windows 命名管道 JSON IPC；找不到 mpv 时降级 `<audio>`。
- **后果**：多一个进程生命周期要管；好处是解码/设备能力与 UI 解耦。

## D-02 客户端单文件、零依赖、无构建

- **状态**：Active
- **背景**：插件要能直接放进 DSH 的插件目录并被 `__ModuleLoader__` 加载。
- **结论**：`client.js` 单文件、手写 `h()`、无打包、无框架依赖。
- **代价**：无类型检查；文件已约 2.4k 行。**未被推翻，但拆分需要单独立项**。

## D-03 播放面板不放在 `shell.overlay`

- **状态**：Active（替代了早期方案）
- **背景**：v1.1/v1.2 两次出现"点不开"。
- **证据**：运行时查询 `shell.overlay` 的 occupant 为 `active:false`；list 型 slot 会把"渲染空/抛错"的条目停用且不再挂载。
- **结论**：面板改为迷你行内部的 `position: fixed` 子组件；三个 slot cell 外加 `ErrorBoundary`；浮层边界用 `key={open}` 每次打开重新武装。
- **被否方案**：继续留在 slot 里，用"永远渲染非空内容"绕过（脆弱，已失败一次）。

## D-04 队列曾是面板内的第二屏，v1.6 暂时移出到音乐库

- **状态**：Superseded（指"第二屏"这一实现形态）——**不代表需求被取消**
- **背景**：v1.5 出现"点队列后面板消失、之后再也打不开"。
- **已知证据**：v1.5 的 `QueuePanel` 与今天实现一致；当时边界 fallback 是可见红框但从未出现；边界无 `key`；队列容器当时是 `overflow:auto` 且无 flex 尺寸。
- **当时的处置**：v1.6 把队列搬到音乐库，属**止血手段**，不是产品目标的改变。
- **与当前目标的关系**：`DESIGN.md` **R06 仍然有效**——播放面板内切换封面与队列、记住上次视图。本决策只放弃"第二屏 + 整块替换 + 无记忆"这一具体做法，不否定 R06。
- **未定论**：当时的真实根因（渲染异常 vs 容器塌陷）**未证实**，记录在此避免后人误以为已结案。
- **后续**：B1（队列空白）修好后再实现 R06；旧音乐库入口的去留见 `DESIGN.md` §5 未决问题 3。

## D-05 队列顺序：`queue` 是用户视图，`plays` 是给 mpv 的materialised 顺序

- **状态**：**Superseded**（2026-11-05，被 D-14 替代）
- **背景**：需要无缝续播（gapless），又要在 UI 上保持用户顺序。
- **结论**：mpv 只镜像 `plays.slice(cursor)`；`baseCursor` 把 mpv 的 `playlist-pos` 映射回 `plays`。手动切歌一律重载文件（确定性），自动切歌交给 mpv（无缝）。
- **后果**：外部媒体控制（SMTC）的 `playlist-next` 只在镜像范围内有效，**队尾不回绕**，与模式语义存在偏差。
- **为什么被替代**：两套顺序意味着两套下标空间，`cursor` 的归属无法从 interface 上判断；B13/B16/B18 都长在这里。见 D-14。

## D-06 淡入淡出用音量斜坡，不做交叉淡化

- **状态**：Active
- **选项**：① 交叉淡化（两条音轨同时解码）；② 淡出→切换→淡入。
- **结论**：②。① 需要双解码与混音，超出当前架构。
- **后果**：自动切歌只能做淡入（mpv 不允许提前降音量），手动切歌才是完整淡出+淡入。

## D-07 Windows 媒体键依赖 mpv 的 SMTC，而非 Electron `globalShortcut`

- **状态**：Open（能力存在，路径未验证）
- **证据**：
  - 运行参数为 `--no-video --force-window=no --no-input-default-bindings`；
  - mpv 的 `--media-controls` 默认 `yes`（Windows only，创建自己的隐藏窗口承载 SMTC）；
  - SMTC 按钮直接映射为 mpv 命令（play/pause/stop/playlist-next/playlist-prev），不经输入绑定；
  - 物理媒体键路径在 `w32_common.c` 的 `WM_APPCOMMAND` 中，需要 VO 窗口；且默认绑定已被关闭。
- **结论**：可行路径是 SMTC，但"会话是否出现在系统媒体浮层""物理键是否路由到它"**均未实测**。
- **被否方案**：在 DSH/Electron 侧接管（宿主没有暴露相关能力；需原生模块，成本高）。

## D-08 艺术家不做文件名推断，改用"专辑艺术家"覆盖

- **状态**：Active
- **背景**：用户库的文件名不含可靠艺术家信息；猜测会制造假数据。
- **结论**：解析器只做保守解析（书名号、序号、年份、音质标注）；艺术家来自数据库覆盖。

## D-09 队列条目身份 = 数组下标（已知薄弱）

- **状态**：**Superseded**（2026-11-05，被 D-15 替代）
- **后果**：重复歌曲时 `plays.indexOf(currentId)` 命中第一条，游标可能定位错误；队列行也无法区分同曲的两条。
- **潜在改法**：引入 `entryId`（影响 `player.js` / `api.js` / 客户端 / 持久化迁移），属高风险跨层改动，未决定。
- **为什么被替代**：entryId 只是把身份搬进队列，会新增第二个身份空间；唯一性让 `trackId` 本身成为稳定键。见 D-15。

## D-10 随机模式每次都重新洗牌（无稳定序列）

- **状态**：**Superseded**（2026-11-05，被 D-16 替代）
- **后果**：任何队列编辑都会触发 `rebuildPlays()` → 重新洗牌；"下一首"会跳到全新随机结果。
- **潜在改法**：保存一轮顺序 + 消费游标，仅在轮次结束再生。属状态机改动，需影响分析。
- **为什么被替代**：洗牌只应发生在"进入随机"和"一轮结束"，队列编辑不再洗牌。见 D-16。

## D-11 测试脚本的副作用（历史遗留，待改）

- **状态**：Open（已登记禁令）
- **事实**：`playback-test.mjs` 与 `loadtest.mjs` 直接打运行中的插件，会覆盖真实队列、写用户设置、改变当前播放，且不恢复。
- **当前处置**：在 `docs/TESTING.md` 列为**禁止自动执行**；计划把主要逻辑迁到隔离 L2。

- **状态**：Active
- **结论**：代码 = 实现事实的证据；`DESIGN.md` 中 Approved = 目标行为的权威；`TESTING.md` = 验证证据。冲突只登记不擅改。

## D-13 时间与随机通过构造参数注入，其余保持自建

- **状态**：Active
- **背景**：淡变按约 16ms 分步（`fadeIn(280)` ≈ 17 次 `setVolume` + 17 次真实等待），
  `shuffle` 用 `Math.random()`。状态机测试若走真实时间，一次跳转 160–460ms，
  整批用例以秒计，且 shuffle 结果不可复现。
- **选项**：① 为测试导出 `rebuildPlays` / `handleEndOfTrack`；② 测试里等真实时间；
  ③ 注入整个 `clock` 抽象；④ 只注入 `delay` 与 `random` 两个函数。
- **结论**：④。`createPlayer` 接受 `delay`（默认 `engine.js` 的 `delay`）与 `random`
  （默认 `Math.random`），生产调用点与默认值完全不变。
- **范围**：只这两个。**不**注入 `now`（没有用例需要固定时间戳）；**不**把淡变算法、
  轮询/持久化定时器、`queue/plays/cursor` 规则做成可替换——那些是产品行为，不是测试接缝。
- **修订（2026-11-14）**：范围加入第三个接缝 `pollMs`（位置轮询周期）。
  **这不是"又找到两个 adapter"，而是一次有意的例外**：本条原句「不把…轮询…定时器做成可替换」被本修订**取代**，
  理由只有一条——不注入就只能让用例真等一秒，而 B35 的竞态要求把"读在途"的窗口摆到测试里。
  可替换的只有**周期**这一个数；轮询的行为（读什么、写到哪、怎么判新旧）仍然不可替换，
  生产默认仍是 1000ms，`lib/host/plugin.js` 不转发它（配置面不变，避免死配置）。
  本条其余排除项（淡变算法、`queue/plays/cursor` 规则、持久化定时器）不受影响。
- **被否方案**：① 污染生产接口；② 慢且不稳定；③ 当前只有一个用途，属过度设计。
- **后果**：以后新增注入点前先问"这里真的有两个 adapter（真实 / 测试）吗"；
  只有一个时不开 seam。

## D-14 队列只保留一条顺序（替代 D-05）

- **状态**：Active（2026-11-05）
- **背景**：B10/B13/B16/B18 四个缺陷的共同根是"两套顺序 + 两套下标空间"。
- **选项**：① 保留 `queue` + `plays`，给下标加命名纪律；② 让 `queue` 同时是可见顺序与播放顺序。
- **结论**：②。`queue` 是唯一顺序；`cursor` 只索引它，由 `commit()` 一个写者维护；mpv 镜像
  `queue.slice(cursor)`，`baseCursor` 仅作为 adapter 偏移。
- **被否方案**：① 需要每个调用点判断"这个数字属于哪个空间"，等于把缺陷留在 interface 里。
- **后果**：随机变成"就地重排"（见 D-16）；退出随机不恢复原顺序；`plays` 与 `rebuildPlays`
  的定位职责一并消失。

## D-15 条目身份 = 唯一 trackId，不引入 entryId（替代 D-09）

- **状态**：Active（2026-11-05）
- **背景**：重复条目让 `indexOf` 有歧义，B13 由此而来。
- **选项**：① 引入 `entryId` + 双写；② 活动队列不允许重复，身份退回 `trackId`。
- **结论**：②。去重只发生在队列入口（`playQueue` / `setQueue` / `enqueue` / 读档恢复）；
  用户播放列表仍允许重复（独立表，与队列无关）。
- **被否方案**：① 新增持久化字段与第二个身份空间，且要迁移。
- **后果**：同一首歌不能在一次队列里出现两次；"下一首播放"对已存在条目是移动，不是复制。

## D-16 随机只重排"当前之后"，退出随机不恢复原序（替代 D-10）

- **状态**：Active（2026-11-05）
- **背景**：进入随机时把当前曲挪到队首会打乱已播放历史；每次编辑都重洗会覆盖"下一首播放"。
- **结论**：进入随机只洗 `queue.slice(cursor+1)`；一轮结束（EOF 在最后一首）整体重洗并回到 0；
  退出随机保留当前可见顺序，**不保存原始顺序**。
- **被否方案**：保存一份隐藏的原始顺序用于还原——那是第二个顺序，正是 D-14 要删掉的东西。
- **后果**：随机是可观察的行为（用户看得见队列被重排）；需要"先排好再随机"的场景要重新拖排。

## D-17 镜像同步由 Engine 确认，Player 从事实推导 cursor（C2）

- **状态**：Active（2026-11-05）
- **背景**：C1 里 Player 自己组合 `trimTail` + `append` + `getProperty('playlist-pos')`，
  并按 `cursor - pos` 计算锚点。命令被接受不等于播放列表达到目标；mpv 在写入期间自然换曲时，
  锚点会基于过期的 pos 计算，cursor 也可能指向已经不再播放的条目。
- **选项**：① 保持"三个动词 + 调用方善后"；② 由 Engine 提供带确认语义的复合操作，
  返回事实，Player 据此推导；③ 引入事务/重试框架。
- **结论**：②。`load()` 与 `rewriteTail({expectCurrent, tail})` 都在 mpv 报告目标条目数后才返回
  `ok`，并返回 `{at, seen, pos, count, currentFile}`；`current-moved` 时不写入并交还事实，
  Player 采纳新当前曲后**再写一次**尾部（有界一次，不循环）。
- **被否方案**：③ 超出问题规模；① 把不变量留在调用方，正是 B14/B17 的来源。
- **后果**：队列编辑的返回值现在可以当作"播放列表已经是这样"的证据；代价是每次写入多几次
  `get_property`，以及 mpv 侧的竞态有了一条**明确可测**的出口（`current-moved`），
  而不是静默错位。`stop` / `pause` 的滞后不在此接口范围内，仍由 Player 的有界等待处理。

## D-18 扫描结局由一个台账统一维护，失败单独计数

- **状态**：Active（2026-11-06）
- **背景**：85 个文件只入库 47 个时，`scan_runs` 仍写 `done` / `error:null`。同一形态有四个出口：
  失败不计数、`skipped` 同时表示"未变化"和"失败"、计数对象在 roots 循环外（跨根累加）、
  收尾不在 `finally`（异常后永久 `running`）。四者指向同一件事：一次扫描的"文件结局集合"没有所有者。
- **选项**：① 在各分支就地补计数器；② 抽一个 run 台账（`indexed / unchanged / failed` + 单一收尾），
  扫描循环只决定"这个文件的结局"；③ 引入通用的任务/阶段恢复框架。
- **结论**：②。台账是 `library.js` 内的私有函数（两个写入口 + 一次 `close()`，不导出给测试）；
  `scan_runs` 增加一列 `failed`（additive、默认 0、`user_version 1→2`），历史行不改写。
- **被否方案**：① 只是给同一个可变袋换标签，跨根累加与"收尾不在 finally"仍然结构上可能；
  ③ 超出问题规模，且当前没有第二个 adapter（见 D-13 的"一个 adapter 不开 seam"）。
- **后果**：`done / partial / error` 有明确判据；`error` 只保留首条原因；部分失败第一次可以被
  `library.scanStatus` 读出来。当时重命名与重叠根的身份问题仍未解，那类故障以 `error` 结束；
  后续的身份与来源规则见 D-19 / D-20。

## D-19 路径用于自动识别已有记录，trackId 是持久身份，扫描不推断文件移动

- **状态**：Active（2026-11-07）
- **背景**：改名后旧行会残留、收藏仍指向旧 id。曾实现过一版"自动指纹合并"（`reconcileIdentity`：
  按 `size:mtime:duration:codec:rate` 匹配消失的行与新行、成功则让旧行吸收新行、失败则记
  `conflicts`；配套加了 `scan_runs.conflicts` 与 schema v3）。实现过程中连续暴露出三个无法回避的
  问题：同一个名字可以被新的真实文件合法复用；两份内容相同的文件是两条真实存在的曲目；
  一旦允许"旧路径上的文件被当成改名结果"，就必须不断为边界补规则（备用 id、盐、冲突计数、
  状态可见性）。产品的核心是播放器，不是推断文件历史的资产管理系统。
- **选项**：① 保留自动指纹合并并继续补规则；② 只按路径判定身份，改名＝新曲目 + 旧行 `missing`；
  ③ 引入内容哈希做身份。
- **结论**：②。`tracks.path`（唯一约束）只用于**自动识别已有记录**：同一路径重扫沿用同一行与同一 id，
  同一路径换内容沿用 id 只更新元数据，不同路径就是不同曲目（内容相同也不合并）。
  `hash(rootId, 相对路径)` 只在"这条路径还没有行"时用来生成新 id。整套自动匹配代码删除，
  `relocateTrack` 删除，`scan_runs.conflicts` 与 schema v3 撤销，库停留在 **v2**。
- **被否方案**：① 每修一个边界就长出一层新规则，而它解决的问题（改名后收藏还在不在）用户
  可以用一步手动操作解决；③ 同样无法区分"两个内容相同的文件"，还要整文件读取。
- **后果**：改名后曲库里会出现两条记录（旧行 `missing`、新路径为新曲目），这是**预期行为**，
  不是缺陷；需要 UI 让 `missing` 可见并提供"定位文件"（Phase 3）。手动重新定位、整文件夹搬家
  都不在本轮，接口与事务边界见 `docs/CURRENT.md` §5。

## D-20 移除来源 = 停止管理，曲目行与引用一律保留

- **状态**：Active（2026-11-07）
- **背景**：`removeRoot` 原本 `DELETE FROM tracks WHERE root_id`，收藏 / 歌单 / 队列里留下无法解析的
  悬挂 id（B21）。而"移除来源"在产品上只表示不再扫描这个文件夹。
- **选项**：① 删除曲目行；② 保留行并标记 `missing`，只删 `roots` 与 `scan_runs`；
  ③ 新增"来源状态"字段或来源状态表。
- **结论**：②。该根的曲目置 `missing = 1`、删 ledger 行、删根行三步放进**一个短事务**
  （局部 `BEGIN IMMEDIATE` / `COMMIT`，不抽通用事务层）：要么整个来源停止管理，要么什么都不变，
  不会留下"根仍注册、曲目却已全部 missing"的半截状态。v2 表结构完全够用：`missing` 表达"当前不可用"，
  `tracks.path` 唯一保证重新添加时按路径命中**同一行**，于是 id、`added_at`、收藏、歌单、覆盖、
  队列引用全部原样恢复；仍不存在的文件保持 `missing`。扫描进行中移除同一来源会被拒绝
  （`scanningRoots` 守卫），否则未结束的遍历会把它写回去。
- **被否方案**：① 与"不删除用户关联"直接矛盾；③ 为一个可以由 `missing` + 路径唯一表达的状态
  新增字段/表，属于给一个问题造一套框架。

## D-24 播放头算术抽成纯函数模块，`client.js` 只留生成副本

- **状态**：Active（2026-11-14）
- **背景**：宿主每秒采样一次播放位置，客户端必须补间；但补间、两端夹取、进度分数、剩余时间
  全都散在 `client.js` 的渲染函数里，**零测试**。取证见 `docs/research/2026-11-13-playhead-architecture.md`：
  media-chrome 的 `range-animation.ts`、video.js 10 的 `TimeCore`、Home Assistant 前端导出的
  `getCurrentProgress` 都把插值放在独立纯单元里；反例是 Plyr，把规则写在 600 行 `controls.timeUpdate()`
  里且无测试——那正是我们今天的形状。同时发现一个真缺陷：`estimateMs` 只夹上界，
  采样时刻晚于当前时钟（时钟小偏差）时位置会变成负数。
- **选项**：① `lib/shared/playhead.js` + 生成进 `client.js` 的标记区 + 一致性守卫；
  ② 在 `client.js` 内划"纯源码区"，测试用 `node:vm` 跑该区；③ 不抽，只补测试。
- **结论**：①。单文件、零构建（D-02）意味着 client 不能相对 `require`、`node --test` 也不能 `import`
  一个浏览器 bundle，所以"同一份算术存在于两处"是**结构性事实**；生成区把它变成可机检的事实
  （`node scripts/inline-playhead.mjs --write` + `test/inline-playhead.test.mjs`），与 `bundle-id`
  的 `--write` + 守卫同一套路。
- **被否方案**：② 隔离靠标记正则，函数体里对闭包变量的**懒引用**（测试没走到的分支）逃得过检查；
  ③ 没有 seam 就没有地方放测试，等于继续靠肉眼。
- **后果**：插值 / 进度分数 / 剩余时间只有一份实现；`positionSampledAt` 只允许出现在生成区内（有守卫），
  `client.js` 的 `estimateMs(player)` 包装层持有**补间时钟**；墙钟读取只剩三类，都与补间无关——
  D-27 的等待判定、队列拖动的 200ms 防误触（`client.js` 的 `lastDragAt`）、以及 toast 与临时键生成。
  本条原措辞（"只有 `Date.now()`"）已被修订；`lib/shared/playhead.js` 成为新的依赖边（`package.json` 的 `files` 已收录）。
- **本轮不改**：seek latch 仍是 `Date.now()` × 1600ms / 900ms 两个魔法数字。按研究结论应改判
  **新旧**（快照采样时刻 vs seek 回报时刻），不是时长；那是状态层的改动，单独一轮。时钟换
  `performance.now()` 同样留到那轮（要先记录"收到快照的时刻"，属状态层）。
  → **已在 D-27 落地**（2026-11-14，同一套生成区与守卫）。

## D-27 seek 的"防回弹"按采样时刻判新旧，插值锚点改用单调时钟

- **状态**：Active（2026-11-14）
- **背景**：D-24 把播放头算术抽进模块后，进度条里还剩两件事没做对：
  ① 定位（seek）后"先跳到目标、再被一秒一次的旧快照拉回去"的抑制，用的是
  `age < 1600ms && |host - pending| > 900ms` 两个时长/距离阈值；
  ② 补间用 `Date.now() - positionSampledAt` 算流逝，而 `Date.now()` 会在 NTP 对时、
  休眠恢复时跳变，跳变直接变成进度条的一次跃动。
- **取证**：`docs/research/2026-11-13-playhead-architecture.md` §1/§4——media-chrome 用
  `performance.now()` 建锚点（`range-animation.ts`）；video.js 10 在 seek 期间**丢弃**旧事件、
  由 `seeked` 收口，**无时长阈值**；用时长阈值兜底的是 video.js 8 时代的做法。我们自己的
  `mpv` 路径还有一个额外事实：宿主在**应用** seek 的同一处写 `positionSampledAt = Date.now()`，
  所以"快照的采样时刻 ≥ 请求发出的时刻"就是"宿主已经看见这次 seek"的证据。
- **选项**：① 缩短阈值（把 1600 调到 300 之类）；② 由宿主回报 seek 序号/完成事件，客户端等它；
  ③ 用已有的两个时间戳判新旧，并给时钟回拨一条明确出口。
- **结论**：③。`resolveSeek(pending, player, wallNowMs)` 的三条规则：采样时刻 ≥ 请求时刻 → 放行；
  请求时刻不可信（≤0）或当前墙钟已回退到请求时刻之前 → 丢弃请求（宁可一帧旧位置，也不冻住进度条）；
  否则继续画请求位置。同时把补间锚点换成**单调时钟**：`anchorOf(player, receivedAtMs)` 在快照对象
  **首次出现**时记下 `performance.now()`，之后 `positionOf(anchor, performance.now())`。
- **被否方案**：① 阈值只是把同一种猜测调小，900ms 那条甚至会在它本该遮住的那张旧快照上提前放行；
  ② 要改 Host↔Client 契约（新增字段 + 影响分析 + 版本对齐），为一个可以用已有时间戳回答的问题
  引入新契约，违反 D-26 的所有权门。
- **后果**：
  - **两种时钟、两个问题**写进模块头注释：补间问"过了多久"（单调时钟），等待问"宿主看见没有"
    （墙钟，唯一两边可比的时间基准）。模块内两个函数各用各的，谁都不读时钟，读数全部由调用方传入。
  - `positionSampledAt` 仍然只出现在生成区里（守卫），组件不再自己判 latch；回归守卫
    `client-source` 新增一条：`ProgressBar` 必须走 `resolveSeek`，且 `1600` / `900` 不得复现。
  - `isAdvancing` 收紧为 `playing === true && paused === false`：宿主两个字段都发，
    缺一个说明快照不完整，"不凭空产生运动"与"没有采样时刻就不补间"是同一条原则。
  - **仍未做**：键盘 seek（←/→、Home/End）不设等待，仍可能短暂回弹——那是另一个交互决定，
    已登记 `docs/CURRENT.md` 待办。
- **补记（2026-11-14，B31）**：补间的锚点必须按**采样**的身份复用，不能按"这次读取"的身份。
  `status` 每次读回都是新对象（1 Hz 轮询，外加每条命令后的补读），同一张采样被重复读到时若重新锚定，
  显示位置就会回退再爬——这正是用户报告的"一卡一卡"。落地为 `nextAnchor(previous, player, now)`：
  采样标识（宿主采样时刻 + 位置 + 时长 + 是否推进）不变就沿用旧锚点。

## D-29 播放/暂停以「有没有文件打开」为准，不以 mpv 的 `pause` 标志为准

- **状态**：Active（2026-11-14）
- **背景**：B30——重启后第一次点播放没有反应、第二次才播。`toggle()` 只读 `engine.state.pause`，
  而**新起的 mpv 进程 `pause` 默认 `no`**、且没有文件打开（`currentFile: null`）。于是第一按被解析成
  `pause()`，对空播放列表是一次 no-op；第二按 `pause === true` 才落到 `resume()` 去加载文件。
- **决定**：`toggle()` 先看**有没有文件打开**：`currentFile === null` → 一律 `api.resume()`
  （由它内部决定"加载"还是"从队尾重来"）；否则按 `engine.state.pause` 分派。
- **理由**：mpv 的 `pause` 描述的是"这个进程是否暂停"，不是"我们有没有东西在播"。空 mpv 的
  `pause: no` 意思是**没有东西可暂停**，不是"正在播放"。
- **影响面**：`lib/host/player.js` 的 `toggle()` 一个分支；不碰游标、队列、`plays`/`baseCursor`、淡变、
  持久化与 API 契约；`resume()` 既有的三条分支（队尾重来 / 暂停续播 / 镜像加载）不变。
- **回退**：单函数单行，`git checkout lib/host/player.js` 即可。
- **验证**：`test/player-transport.test.mjs` 两例——「the first press on a cold engine starts playback
  instead of pausing (B30)」用 `stored` 重放重启后的恢复态（队列 + 游标 + 位置 1500ms + 空引擎），
  断言不发 `pause`、发出 `load`、起点 1500ms、快照 `playing: true`；另一例守住"已加载且正在播时按下仍是暂停"，
  防止修 B30 顺手把正常暂停也改掉。
- **被否方案**：客户端先按快照猜"是否播放中"再决定发 `player.play` 还是 `player.pause`——同一个歧义
  被搬到客户端，且每个调用点各判一次。

## D-30 每帧写入必须先确认"值变了"

- **状态**：Active（2026-11-14）
- **背景**：B32——暂停后进度条仍抖。排除了宿主（暂停时位置 10 Hz 采样 6 秒无任何变化）与 CSS
  （fill 上没有 transition / keyframes）之后，剩下的是**写**：`paint()` 每帧无条件写 `--p` 和气泡文本，
  一秒 120 次，而 `--p` 驱动的 `left: calc()` 与 `scaleX()` 每次失效都会重新对齐到设备像素——
  静止时就表现为约 1px 的抖动。同一文件里的两个时间读数早就有 `value !== last` 守卫，只有进度条漏了。
- **决定**：rAF 驱动的绘制**一律走"变化判定"**：判定做成纯函数（`nextPaint(previous, next)`），
  返回 `write: false` 时调用方必须直接返回、不碰 DOM。分数按 1e-5 量化（在宽条上约 1/100 像素），
  低于该量级的变化不算移动。
- **理由**：值没变时写 DOM 是**纯成本**——失效样式与布局、让子像素重新取整，收益为零。
  这条与 D-22 同源：D-22 管"动效该不该有"，本条管"没有动效的时候也别动"。
- **后果**：暂停时一秒一次写入降为一次（首帧）；播放时仍每帧写（那是真变化，也是平滑的来源）；
  守卫钉在 `test/client-source.test.mjs`，纯函数语义钉在 `test/playhead.test.mjs`
  （含"10 秒暂停 = 1 次绘制，而不是 1200 次"）。
- **被否方案**：把整条进度条交给 CSS `transition` 平滑（值仍在每帧变，只是把抖动藏进插值，
  且与"不动的时候别动"相悖）；只在暂停时停掉 rAF（值仍可能在播放时被重复写，且需要额外状态）。

## D-31 会"冻结"播放位置的传输操作必须自己盖章

- **状态**：Active（2026-11-14）
- **背景**：B33——暂停后进度条还会动一下。宿主的位置只在两处更新：1 Hz 轮询与 `seek()`。
  `pause()` 不更新，于是"暂停确认"的那张快照带着**最多落后一秒**的 `positionMs`：
  客户端已经插值画到真实位置，被这张旧快照按回去，下一次轮询再把真值送来 → 先回缩再前跳。
- **决定**：任何**会冻结位置**的传输操作，在引擎确认之后立刻读一次 `time-pos`，
  写回 `positionMs` 与 `positionSampledAt`，然后才 `notify`。当前只有 `pause()` 符合这个定义
  （`seek()` 一直如此；`resume()` 不冻结，位置不变；`stop()`/重载会重置位置）。
- **理由**：快照是"宿主此刻的事实"。位置已经停止推进，而快照还说着一秒前的位置，
  这张快照就是错的——客户端的插值没有错，它只是被一份过期的权威值纠正。
- **影响面**：`lib/host/player.js` 的 `pause()` 增加一次 `getProperty('time-pos')` 与两个字段赋值；
  未加载文件时跳过；读失败则退回旧行为（下一次轮询修正）。不改快照形状、不改 API、不碰游标/队列/持久化。
  附带收益：`schedulePersist()` 存下的暂停位置也从"最多差一秒"变成准确值。
- **回退**：单函数，`git checkout lib/host/player.js`。
- **验证**：`test/player-transport.test.mjs` 的「pausing … stamps where it stopped (B33)」——
  用"轮询 41.6s / 引擎真值 42.5s / 客户端已画到约 42.3s"重放，断言暂停快照的位置**等于引擎真值**
  且**不落后于已画值**。变异（去掉盖章）→ 该例红。
- **被否方案**：客户端做"显示位置只增不减"的防护——那会把合法的向后 seek 也一起压住，
  且等于让界面发明一个宿主不同意的值；权威在宿主，错的地方就该在宿主修。

## D-32 状态响应按「发出顺序」定序，旧答案一律丢弃

- **状态**：Active（2026-11-14）
- **背景**：B34——暂停后**有概率**回缩一下再前进。根因不是补间，是**竞态**：
  客户端有两条 `status` 请求源（1 Hz 轮询、每条命令后的补读），没有任何定序；而命令在宿主侧要
  等淡出与 mpv 确认（约 200 ms），所以点击前发出的轮询可以被服务并返回在"暂停答案"之后。
  把它应用上去，锚点回到旧位置、`advancing` 重新为真 → 条先回缩、下一次轮询再前跳。
- **取证与先例**：`docs/research/2026-11-13-playhead-architecture.md` §1/§4——video.js 10 在 seek
  期间**丢弃**时间更新而不是把它平滑掉；Spotify Web Playback SDK 每次只给一个有序的 state 对象。
  **没有任何一家用"重新锚定到旧答案"来表示暂停。**
- **决定**：请求在**发出时**编号（`statusSeq += 1`），响应回来时与"已应用的编号"比较
  （`acceptResponse(lastAppliedId, requestId)`），更旧的直接丢弃、连 session 都不碰。
- **为什么不用宿主的 `uptimeMs`**：它等于 `Date.now() - startedAt`，宿主重启会归零、NTP 跳变会倒退，
  用它定序需要额外的"重启检测/跳变阈值"魔数。编号由客户端自己产生，天然单调，与任何时钟无关。
- **代价**：极少数情况下会丢掉一张"其实更晚被服务"的响应（先发的请求被更晚服务），
  代价是那一帧少一次刷新，下一次轮询补上；换来的是**永不回退**的播放头。
- **验证**：`test/playhead.test.mjs` 的「a late, older answer must not move the bar backwards」——
  把概率钉成确定的到达顺序（先到暂停答案、后到旧轮询答案），断言已应用编号保持 2、绘制序列为
  `[100900]`；`test/client-source.test.mjs` 另有守卫：编号在发出时、判定在 `session.setStatus` 之前。
  变异（门恒开 / 客户端去掉门）两处各自 Red。
- **被否方案**：用 `uptimeMs` 定序（见上）；在宿主加 `seq` 字段（改返回结构属 §4 高风险，为一个
  客户端本可自答的问题开契约，违反 D-26 的所有权门）；客户端"显示只增不减"（会压死合法向后 seek）。
- **补记（2026-11-14，`/code-review` 后）**：门控也盖住**失败路径**。原先只有成功分支比较编号，
  `catch` 里照样 `session.set({ phase: 'error' })`——一条更旧请求的失败能盖掉已经落地的新答案。
  现在失败分支同样先 `acceptResponse`，且**落地后也推进编号**，让更旧的成功能答不能复活它。
  守卫：`test/client-source.test.mjs` 的 B34 用例（新增三条断言，先红后绿）。

## D-33 轮询写回播放头必须按「代」判定，不按时间戳

- **状态**：Active（2026-11-14）
- **背景**：B35——同一个"暂停后回缩"症状被修了三次（B32 绘制、B33 盖章、B34 响应定序）仍在。
  真正的写入者在宿主：1 Hz 轮询先 `await engine.getProperty('time-pos')` 再赋值，而这次读会**跨过**
  一次暂停或 seek，返回的是跨越**之前**的位置，却被打上**之后**的 `positionSampledAt`。
  客户端看到"更晚的采样 + 更小的位置"，唯一的读法就是"条退回去了"。
- **为什么前三轮抓不到（这才是本条的教训）**：夹具引擎的 `getProperty` **同步返回**，
  于是"读在途"这一段在测试里物理上不存在；每个闭环都只能在同步世界里自证。
  本轮给夹具加了「挂起下一次读取、并在释放时返回读取开始那一刻的值」，才把这个竞态变成可复现。
  教训：**替身比被测对象更同步，等于把所有竞态从测试里删掉。**
- **决定**：`state.positionMs` 改成访问器，**每次写入都 `playheadGeneration += 1`**；轮询在读之前记下代数，
  读回来时代数变了就丢弃这次采样。判断的是"有没有人在这期间写过播放头"，不是"谁的时间戳更大"。
- **为什么不用时间戳比较**：先试过 `issuedAt >= state.positionSampledAt`，实测日志里出现
  `issuedAt === stamp === …426`（同毫秒并列）→ 判定放行 → 仍然回缩。毫秒精度不足以表达"先后"。
- **附带收益**：访问器保证**所有**写入点都会作废在途读取，包括 load / stop / restore 这些老站点，
  不需要逐处记得加一行。
- **影响面**：`lib/host/player.js` 一个访问器 + 轮询里的一个比较；`createPlayer` 新增可注入
  `pollMs`（沿用 D-13 的接缝纪律：真实 1000ms、测试 200ms/5ms，两个 adapter 才开 seam）。
  快照形状、API、游标、队列、持久化均不变。
- **回退**：`git checkout lib/host/player.js`。
- **验证**：`test/player-transport.test.mjs` 的「a poll that was already reading must not overwrite the
  pause stamp (B35)」——挂起读取 → 暂停盖章 42.5s → 释放（返回 41.6s）→ 250ms 内每 2ms 采样一次，
  观察到的位置集合必须只有 `{42500}`。变异（去掉代数比较）5/5 全红；修复后连跑 10 次全绿。
- **被否方案**：客户端"显示只增不减"（压死合法向后 seek，且让界面发明宿主不同意的值）；
  暂停时停掉轮询（暂停后位置仍需采样，且不能覆盖 seek 的同款竞态）。
- **补记（2026-11-14，`/code-review` 后）**：写入收口为 `stampPosition(ms)`——位置与采样时刻成对写，
  全仓只剩一处 `state.positionSampledAt = Date.now()`。访问器只盖住 `positionMs`（成对的字段只护了一半，
  这正是 review 点出的 Data Clump），收口后轮询 / 暂停 `seek()` 三份同形代码一并消失。
  `clear()` 是唯一例外："哪儿都不是"要把两半都清零，否则是一个空位置配一个新时间戳。
  守卫：`test/player-source.test.mjs` 三条（写入点唯一 / 三个写入者都用它 / `clear()` 清两半），
  变异（把 `seek` 改回手写）会红。

## D-34 进度条与音量条换原生 `<input type="range">`，不是换 role

- **状态**：**Superseded**（2026-11-15，被 D-36 取代）——取证链保留在这里，
  但结论里"焦点、键盘、指针拖动都由 UA 提供"那句不再成立：用户不要任何键盘操作，
  D-36 用 `tabIndex={-1}` 把滑条移出 Tab 序列，也不再承诺键盘路径。
- **背景**：D-28 为"不留错误的无障碍声明"，把进度条从 `role="slider"` 改成 `progressbar`、音量条改成
  `meter`。该动作依据的是一句当时**没有来源**的判断。取证（`docs/research/2026-11-14-slider-progressbar-a11y.md`）结论：
  1. ARIA 1.2 对 `slider` 只规定 `aria-valuenow` 为 MUST，方向键原文是 "typically possible"，**没有 MUST/SHOULD**；
     键盘模型出自 APG，而 APG 自述"does not specify normative requirements"。
  2. 能支撑"声明错误"的是 **WCAG SC 2.1.1**：功能要能通过键盘完成，判据是"**同等或可比的键盘路径**"，
     不是"这个 div 必须可聚焦"。
  3. **`progressbar` 被 ARIA 原文定为只读**：「It is not possible for the user to alter the value of a progressbar
     because it is always read-only.」而我们**保留了指针拖动**（`client.js` 的 `onPointerDown/Move/Up` 连续调用
     `seekTo()`），于是新声明与事实直接相反——**比它替换掉的声明更假**。`meter` 同样不恰当：音量是用户设定的
     输入值，不是 gauge，且 `meter` 连 `aria-readonly` 都不支持。
- **决定**：恢复"可交互"的语义，走**平台能力**：两个控件都换成原生 `<input type="range">`
  （ARIA in HTML：隐式 `role=slider`；焦点、键盘、指针拖动都由 UA 提供，插件一行键位判定都不写，
  因此与 D-28 不冲突）。换来之前，`progressbar` / `meter` 作为**临时豁免**保留，理由与到期条件登记在
  `LIMITATIONS.md` B36。
- **被否方案**：① 恢复 `role="slider"` + `tabindex` + 插件自处理方向键——与 D-28 正面冲突；
  ② 改成真正只读的 `progressbar` 并移除指针拖动——与 R04（点击定位与拖动）冲突；
  ③ 现状（可拖 + 声明只读）——取证已判定为三者中最差的。
- **后果**：属交互模式变化，`AGENTS.md` §16 五步必须走（视觉补偿：`appearance: none` + 现有
  `.dshm-progress-*` 的观感要重新落一遍，滑块与轨道的绘制从自绘变成伪元素）；排在 `docs/CURRENT.md` §5。
- **验证**：换完后 L1 里 `client.js` 不得再出现 `role: 'progressbar'` / `role: 'meter'`；人工核对
  键盘 Tab 能进、方向键能改、拖动仍可用、视觉与现在同族（`TESTING.md` §2.4 + L3）。

## D-35 R15 的「3 秒」用宿主内插值判，不用 1 Hz 采样值

- **状态**：Active（2026-11-14）
- **背景**：R15 的规则是"播放位置 > 3 秒"，而 `state.positionMs` 由 1 Hz 轮询写入，播放中最旧可差约 1 秒。
  `/code-review` 指出：真实的 3.0–4.0 s 区间可能读到 ≤3000 而**直接上一曲**，规则在边界上不确定。
- **选项**：① 保持采样值；② 累计"本曲已播时长"（单调时钟 + 暂停累计）；③ 宿主内插值。
- **结论**：③。`currentPositionMs()` 用 `positionOf()`（**与客户端同一份算术**，`lib/shared/playhead.js`）：
  `positionMs + (playing ? now − positionSampledAt : 0)`，并按 duration 夹取。两个时间戳都是**本进程**的
  `Date.now()`，没有客户端那种跨进程偏差；暂停时校正为零，直接返回 B33 盖章后的准确位置。
- **被否方案**：① 边界不确定，正是本条要修的；② 要维护暂停累计，等于再长一个状态，而插值已经是现成的。
- **影响面**：`lib/host/player.js` 新增 `isPlayingNow()`（快照与规则共用一份"是否在播"）与 `currentPositionMs()`；
  `prev()` 改用它；不碰游标、队列、持久化、契约、快照字段。
- **回退**：`prev()` 一行换回 `state.positionMs`。
- **验证**：`test/player-transport.test.mjs` 两例——① 采样 2.5 s、真实已到 3.1 s（等 600ms）→ 必须**重播**；
  ② 暂停在 2.6 s → 必须**回上一首**（校正为零）。变异（换回采样值）→ ① 红。

## D-36 滑条换原生 `<input type="range">`：只借平台的指针，不承诺键盘路径

- **状态**：Active（2026-11-15）。**替代 D-34**；D-28 的"不绑键"不变。
- **背景**：D-34 决定"两个滑条换成原生 range，因为焦点、键盘、指针都由 UA 提供"。
  用户 2026-11-15 否掉了最后半句：**插件不要有任何键盘操作**。
  把这句话拆开（取证见 `docs/research/2026-11-14-slider-progressbar-a11y.md`，原型见
  `prototype/2026-11-15-native-range/`），它同时指三件互不相同的事：

  1. **键位绑定**：插件自己写 keydown 判定。现状为零（D-28），本轮不变。
  2. **Tab 停靠点**：控件出现在宿主的 Tab 序列里。**这是本轮唯一真正要决定的事。**
  3. **键盘路径**：用键盘把值改掉的能力。**做不到"零"**——只要控件还是表单控件，
     平台就会在它持有焦点时响应方向键；要连这个都去掉，只能回到自绘 `div`。

- **决定**：
  - `ProgressBar` / `VolumeBar` 渲染 `<input type="range">`（`appearance: none` + `::-webkit-slider-*`），
    指针拖动（含拖出边界）、触摸、强制色交给平台；
  - 两条滑条都带 `tabIndex={-1}`：**插件不向宿主的 Tab 序列新增停靠点**（本轮唯一的键盘侧承诺）；
  - 插件仍然不写任何键位判定（D-28 不变）；点过滑条之后方向键仍然有效，那是平台行为，我们不拦
    （拦它就是写键位判定）；
  - 视觉与今天同族：轨 4/3px、悬停 6/5px、滑块 12/10px、命中区 20/10px（`DESIGN.md` §7 不变）。

- **参数**（都落在代码常量与注释上，单点可改）：
  - `SEEK_STEP_MS = 1000`。**键盘步进 = 控件值的量化步长**，两者是同一个数：`range` 的 value 只能落在 step 网格上。
    取 1s 是因为可视反馈是右侧时间读数（秒级），0.25s 的按键在读数上看不出变化；代价是滑块每秒跳约 1.24px（266px 宽）。
  - 填充跟**宿主插值**（`--p`），滑块跟**量化后的值**：填充最多领先一步（1.24px），藏在 12px 滑块底下。
    反过来（填充也跟 value）会让整条 1 Hz 跳一次，原型里对比过，更难看。
  - 值夹在最后一个整步（`floor(duration/1000)*1000`）：range 装不下网格外的值，最后不到 1s 不可选。

- **代价（必须说清）**：
  - **SC 2.1.1 未满足**：指针能改、键盘用户没有同等路径。这是主动选择，登记 `LIMITATIONS` **B37**（D-21 单人自用）。
    它与 B36 的"假声明"性质不同：`role=slider` 是控件自己的语义（可设值的输入），没有说谎。
  - 依赖非标准伪元素 `::-webkit-slider-*`（MDN 明示 non-standard）。D-21 只对齐一个上游（Chromium），记在此备查。
  - 命中区仍是 20/10px，低于 SC 2.5.8 的 24×24（带间距例外，例外是否覆盖我们**待核**）；
    是否抬到 24 是独立提案，排在 `docs/CURRENT.md` §5。

- **被否方案**：
  - 保留 Tab 可达（D-34 原样）：用户明确不要插件插入宿主的焦点序列。
  - 自绘 `div` + `role="slider"` + `tabIndex={-1}`：真"零键盘"，但拿掉的正是本轮全部收益，
    且 D-28 守卫里那句"理由"要重写。
  - 真只读 `progressbar` + 删拖动：最合规，但 **R04 作废**。
  - `step="any"`：实测方向键仍在动，但步长由 UA 定（这里约 2% 量程/按），不可设计。

- **落地（三条工程结论，都是原型先撞出来的）**：
  1. **一次 seek 在途**（`planSeek` / `settleSeek`，`lib/shared/playhead.js`）：两条请求同时在途时，
     前一次的盖章会满足后一次的闩锁，条先退一下再进。串行化之后 `resolveSeek` 的假设才成立。
     原型实测：连按三次方向键只走了两步。
  2. 拖动中不写 `value`（控件才是真值来源）；静止时不写气泡文本（它 `opacity: 0`，写了也看不见）；
     值没变不写 `--p`（D-30 不变）。
  3. 首次绘制走 `useLayoutEffect`：否则静止的条会先画 0 再跳到真实位置，闪一帧。

- **守卫**：`test/client-source.test.mjs` 的「both bars are native ranges and neither is a tab stop (D-36)」——
  `type: 'range'` 与 `tabIndex: -1` 必须成对出现且各两处；`role: 'progressbar' / 'meter'` 不得复现；
  无 `onKeyDown` / `onKeyUp` / `onKeyPress`。D-28 那条改为"`tabIndex` 不再无条件禁止，成对规则见上"。

  真实 CSS 用 headless Edge 单独渲染核对（不走宿主）。**L3 四条**见 `docs/handoffs/2026-11-15.md` §5。
