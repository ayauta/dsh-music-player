# DECISIONS.md — 重要决策与替代方案

只记录**会影响后续长期实现**的决策：背景、选项、结论、被否方案、后果。
流水账式版本变化不进这里（见 `CHANGELOG.md`，待建）。

状态：`Active`（仍然有效）/ `Superseded`（被后续决策替代）/ `Open`（未定）。

---

## D-01 播放引擎：独立 mpv 进程 + 命名管道 IPC

- **状态**：Active
- **背景**：需要真正的 Hi-Res 解码、无缝续播、独占设备能力；Electron 的 `<audio>` 做不到。
- **选项**：① 渲染进程 `<audio>`；② 主进程原生音频模块；③ 独立 mpv 进程。
- **结论**：③。Node 侧监督 mpv，Windows 命名管道 JSON IPC；找不到 mpv 时降级 `<audio>`。
- **后果**：多一个进程生命周期要管；好处是解码/设备能力与 UI 解耦。

## D-02 客户端单文件、零依赖、无构建

- **状态**：Active
- **背景**：插件要能直接放进 DSH 的插件目录并被 `__ModuleLoader__` 加载。
- **结论**：`client.js` 单文件、手写 `h()`、无打包、无框架依赖。
- **代价**：无类型检查；文件已约 2.4k 行。**未被推翻，但拆分需要单独立项**。

## D-03 播放面板不放在 `shell.overlay`

- **状态**：Active（替代了早期方案）
- **背景**：v1.1/v1.2 两次出现"点不开"。
- **证据**：运行时查询 `shell.overlay` 的 occupant 为 `active:false`；list 型 slot 会把"渲染空/抛错"的条目停用且不再挂载。
- **结论**：面板改为迷你行内部的 `position: fixed` 子组件；三个 slot cell 外加 `ErrorBoundary`；浮层边界用 `key={open}` 每次打开重新武装。
- **被否方案**：继续留在 slot 里，用"永远渲染非空内容"绕过（脆弱，已失败一次）。

## D-04 队列曾是面板内的第二屏，v1.6 暂时移出到音乐库

- **状态**：Superseded（指"第二屏"这一实现形态）——**不代表需求被取消**
- **背景**：v1.5 出现"点队列后面板消失、之后再也打不开"。
- **已知证据**：v1.5 的 `QueuePanel` 与今天实现一致；当时边界 fallback 是可见红框但从未出现；边界无 `key`；队列容器当时是 `overflow:auto` 且无 flex 尺寸。
- **当时的处置**：v1.6 把队列搬到音乐库，属**止血手段**，不是产品目标的改变。
- **与当前目标的关系**：`DESIGN.md` **R06 仍然有效**——播放面板内切换封面与队列、记住上次视图。本决策只放弃"第二屏 + 整块替换 + 无记忆"这一具体做法，不否定 R06。
- **未定论**：当时的真实根因（渲染异常 vs 容器塌陷）**未证实**，记录在此避免后人误以为已结案。
- **后续**：B1（队列空白）修好后再实现 R06；旧音乐库入口的去留见 `DESIGN.md` §5 未决问题 3。

## D-05 队列顺序：`queue` 是用户视图，`plays` 是给 mpv 的materialised 顺序

- **状态**：**Superseded**（2026-11-05，被 D-14 替代）
- **背景**：需要无缝续播（gapless），又要在 UI 上保持用户顺序。
- **结论**：mpv 只镜像 `plays.slice(cursor)`；`baseCursor` 把 mpv 的 `playlist-pos` 映射回 `plays`。手动切歌一律重载文件（确定性），自动切歌交给 mpv（无缝）。
- **后果**：外部媒体控制（SMTC）的 `playlist-next` 只在镜像范围内有效，**队尾不回绕**，与模式语义存在偏差。
- **为什么被替代**：两套顺序意味着两套下标空间，`cursor` 的归属无法从 interface 上判断；B13/B16/B18 都长在这里。见 D-14。

## D-06 淡入淡出用音量斜坡，不做交叉淡化

- **状态**：Active
- **选项**：① 交叉淡化（两条音轨同时解码）；② 淡出→切换→淡入。
- **结论**：②。① 需要双解码与混音，超出当前架构。
- **后果**：自动切歌只能做淡入（mpv 不允许提前降音量），手动切歌才是完整淡出+淡入。

## D-07 Windows 媒体键依赖 mpv 的 SMTC，而非 Electron `globalShortcut`

- **状态**：Open（能力存在，路径未验证）
- **证据**：
  - 运行参数为 `--no-video --force-window=no --no-input-default-bindings`；
  - mpv 的 `--media-controls` 默认 `yes`（Windows only，创建自己的隐藏窗口承载 SMTC）；
  - SMTC 按钮直接映射为 mpv 命令（play/pause/stop/playlist-next/playlist-prev），不经输入绑定；
  - 物理媒体键路径在 `w32_common.c` 的 `WM_APPCOMMAND` 中，需要 VO 窗口；且默认绑定已被关闭。
- **结论**：可行路径是 SMTC，但"会话是否出现在系统媒体浮层""物理键是否路由到它"**均未实测**。
- **被否方案**：在 DSH/Electron 侧接管（宿主没有暴露相关能力；需原生模块，成本高）。

## D-08 艺术家不做文件名推断，改用"专辑艺术家"覆盖

- **状态**：Active
- **背景**：用户库的文件名不含可靠艺术家信息；猜测会制造假数据。
- **结论**：解析器只做保守解析（书名号、序号、年份、音质标注）；艺术家来自数据库覆盖。

## D-09 队列条目身份 = 数组下标（已知薄弱）

- **状态**：**Superseded**（2026-11-05，被 D-15 替代）
- **后果**：重复歌曲时 `plays.indexOf(currentId)` 命中第一条，游标可能定位错误；队列行也无法区分同曲的两条。
- **潜在改法**：引入 `entryId`（影响 `player.js` / `api.js` / 客户端 / 持久化迁移），属高风险跨层改动，未决定。
- **为什么被替代**：entryId 只是把身份搬进队列，会新增第二个身份空间；唯一性让 `trackId` 本身成为稳定键。见 D-15。

## D-10 随机模式每次都重新洗牌（无稳定序列）

- **状态**：**Superseded**（2026-11-05，被 D-16 替代）
- **后果**：任何队列编辑都会触发 `rebuildPlays()` → 重新洗牌；"下一首"会跳到全新随机结果。
- **潜在改法**：保存一轮顺序 + 消费游标，仅在轮次结束再生。属状态机改动，需影响分析。
- **为什么被替代**：洗牌只应发生在"进入随机"和"一轮结束"，队列编辑不再洗牌。见 D-16。

## D-11 测试脚本的副作用（历史遗留，待改）

- **状态**：Open（已登记禁令）
- **事实**：`playback-test.mjs` 与 `loadtest.mjs` 直接打运行中的插件，会覆盖真实队列、写用户设置、改变当前播放，且不恢复。
- **当前处置**：在 `docs/TESTING.md` 列为**禁止自动执行**；计划把主要逻辑迁到隔离 L2。

## D-12 文档权威边界

- **状态**：Active
- **结论**：代码 = 实现事实的证据；`DESIGN.md` 中 Approved = 目标行为的权威；`TESTING.md` = 验证证据。冲突只登记不擅改。

## D-13 时间与随机通过构造参数注入，其余保持自建

- **状态**：Active
- **背景**：淡变按约 16ms 分步（`fadeIn(280)` ≈ 17 次 `setVolume` + 17 次真实等待），
  `shuffle` 用 `Math.random()`。状态机测试若走真实时间，一次跳转 160–460ms，
  整批用例以秒计，且 shuffle 结果不可复现。
- **选项**：① 为测试导出 `rebuildPlays` / `handleEndOfTrack`；② 测试里等真实时间；
  ③ 注入整个 `clock` 抽象；④ 只注入 `delay` 与 `random` 两个函数。
- **结论**：④。`createPlayer` 接受 `delay`（默认 `engine.js` 的 `delay`）与 `random`
  （默认 `Math.random`），生产调用点与默认值完全不变。
- **范围**：只这两个。**不**注入 `now`（没有用例需要固定时间戳）；**不**把淡变算法、
  轮询/持久化定时器、`queue/plays/cursor` 规则做成可替换——那些是产品行为，不是测试接缝。
- **被否方案**：① 污染生产接口；② 慢且不稳定；③ 当前只有一个用途，属过度设计。
- **后果**：以后新增注入点前先问"这里真的有两个 adapter（真实 / 测试）吗"；
  只有一个时不开 seam。

## D-14 队列只保留一条顺序（替代 D-05）

- **状态**：Active（2026-11-05）
- **背景**：B10/B13/B16/B18 四个缺陷的共同根是"两套顺序 + 两套下标空间"。
- **选项**：① 保留 `queue` + `plays`，给下标加命名纪律；② 让 `queue` 同时是可见顺序与播放顺序。
- **结论**：②。`queue` 是唯一顺序；`cursor` 只索引它，由 `commit()` 一个写者维护；mpv 镜像
  `queue.slice(cursor)`，`baseCursor` 仅作为 adapter 偏移。
- **被否方案**：① 需要每个调用点判断"这个数字属于哪个空间"，等于把缺陷留在 interface 里。
- **后果**：随机变成"就地重排"（见 D-16）；退出随机不恢复原顺序；`plays` 与 `rebuildPlays`
  的定位职责一并消失。

## D-15 条目身份 = 唯一 trackId，不引入 entryId（替代 D-09）

- **状态**：Active（2026-11-05）
- **背景**：重复条目让 `indexOf` 有歧义，B13 由此而来。
- **选项**：① 引入 `entryId` + 双写；② 活动队列不允许重复，身份退回 `trackId`。
- **结论**：②。去重只发生在队列入口（`playQueue` / `setQueue` / `enqueue` / 读档恢复）；
  用户播放列表仍允许重复（独立表，与队列无关）。
- **被否方案**：① 新增持久化字段与第二个身份空间，且要迁移。
- **后果**：同一首歌不能在一次队列里出现两次；"下一首播放"对已存在条目是移动，不是复制。

## D-16 随机只重排"当前之后"，退出随机不恢复原序（替代 D-10）

- **状态**：Active（2026-11-05）
- **背景**：进入随机时把当前曲挪到队首会打乱已播放历史；每次编辑都重洗会覆盖"下一首播放"。
- **结论**：进入随机只洗 `queue.slice(cursor+1)`；一轮结束（EOF 在最后一首）整体重洗并回到 0；
  退出随机保留当前可见顺序，**不保存原始顺序**。
- **被否方案**：保存一份隐藏的原始顺序用于还原——那是第二个顺序，正是 D-14 要删掉的东西。
- **后果**：随机是可观察的行为（用户看得见队列被重排）；需要"先排好再随机"的场景要重新拖排。

## D-17 镜像同步由 Engine 确认，Player 从事实推导 cursor（C2）

- **状态**：Active（2026-11-05）
- **背景**：C1 里 Player 自己组合 `trimTail` + `append` + `getProperty('playlist-pos')`，
  并按 `cursor - pos` 计算锚点。命令被接受不等于播放列表达到目标；mpv 在写入期间自然换曲时，
  锚点会基于过期的 pos 计算，cursor 也可能指向已经不再播放的条目。
- **选项**：① 保持"三个动词 + 调用方善后"；② 由 Engine 提供带确认语义的复合操作，
  返回事实，Player 据此推导；③ 引入事务/重试框架。
- **结论**：②。`load()` 与 `rewriteTail({expectCurrent, tail})` 都在 mpv 报告目标条目数后才返回
  `ok`，并返回 `{at, seen, pos, count, currentFile}`；`current-moved` 时不写入并交还事实，
  Player 采纳新当前曲后**再写一次**尾部（有界一次，不循环）。
- **被否方案**：③ 超出问题规模；① 把不变量留在调用方，正是 B14/B17 的来源。
- **后果**：队列编辑的返回值现在可以当作"播放列表已经是这样"的证据；代价是每次写入多几次
  `get_property`，以及 mpv 侧的竞态有了一条**明确可测**的出口（`current-moved`），
  而不是静默错位。`stop` / `pause` 的滞后不在此接口范围内，仍由 Player 的有界等待处理。

## D-18 扫描结局由一个台账统一维护，失败单独计数

- **状态**：Active（2026-11-06）
- **背景**：85 个文件只入库 47 个时，`scan_runs` 仍写 `done` / `error:null`。同一形态有四个出口：
  失败不计数、`skipped` 同时表示"未变化"和"失败"、计数对象在 roots 循环外（跨根累加）、
  收尾不在 `finally`（异常后永久 `running`）。四者指向同一件事：一次扫描的"文件结局集合"没有所有者。
- **选项**：① 在各分支就地补计数器；② 抽一个 run 台账（`indexed / unchanged / failed` + 单一收尾），
  扫描循环只决定"这个文件的结局"；③ 引入通用的任务/阶段恢复框架。
- **结论**：②。台账是 `library.js` 内的私有函数（两个写入口 + 一次 `close()`，不导出给测试）；
  `scan_runs` 增加一列 `failed`（additive、默认 0、`user_version 1→2`），历史行不改写。
- **被否方案**：① 只是给同一个可变袋换标签，跨根累加与"收尾不在 finally"仍然结构上可能；
  ③ 超出问题规模，且当前没有第二个 adapter（见 D-13 的"一个 adapter 不开 seam"）。
- **后果**：`done / partial / error` 有明确判据；`error` 只保留首条原因；部分失败第一次可以被
  `library.scanStatus` 读出来。当时重命名与重叠根的身份问题仍未解，那类故障以 `error` 结束；
  后续的身份与来源规则见 D-19 / D-20。

## D-19 路径用于自动识别已有记录，trackId 是持久身份，扫描不推断文件移动

- **状态**：Active（2026-11-07）
- **背景**：改名后旧行会残留、收藏仍指向旧 id。曾实现过一版"自动指纹合并"（`reconcileIdentity`：
  按 `size:mtime:duration:codec:rate` 匹配消失的行与新行、成功则让旧行吸收新行、失败则记
  `conflicts`；配套加了 `scan_runs.conflicts` 与 schema v3）。实现过程中连续暴露出三个无法回避的
  问题：同一个名字可以被新的真实文件合法复用；两份内容相同的文件是两条真实存在的曲目；
  一旦允许"旧路径上的文件被当成改名结果"，就必须不断为边界补规则（备用 id、盐、冲突计数、
  状态可见性）。产品的核心是播放器，不是推断文件历史的资产管理系统。
- **选项**：① 保留自动指纹合并并继续补规则；② 只按路径判定身份，改名＝新曲目 + 旧行 `missing`；
  ③ 引入内容哈希做身份。
- **结论**：②。`tracks.path`（唯一约束）只用于**自动识别已有记录**：同一路径重扫沿用同一行与同一 id，
  同一路径换内容沿用 id 只更新元数据，不同路径就是不同曲目（内容相同也不合并）。
  `hash(rootId, 相对路径)` 只在"这条路径还没有行"时用来生成新 id。整套自动匹配代码删除，
  `relocateTrack` 删除，`scan_runs.conflicts` 与 schema v3 撤销，库停留在 **v2**。
- **被否方案**：① 每修一个边界就长出一层新规则，而它解决的问题（改名后收藏还在不在）用户
  可以用一步手动操作解决；③ 同样无法区分"两个内容相同的文件"，还要整文件读取。
- **后果**：改名后曲库里会出现两条记录（旧行 `missing`、新路径为新曲目），这是**预期行为**，
  不是缺陷；需要 UI 让 `missing` 可见并提供"定位文件"（Phase 3）。手动重新定位、整文件夹搬家
  都不在本轮，接口与事务边界见 `docs/CURRENT.md` §6。

## D-20 移除来源 = 停止管理，曲目行与引用一律保留

- **状态**：Active（2026-11-07）
- **背景**：`removeRoot` 原本 `DELETE FROM tracks WHERE root_id`，收藏 / 歌单 / 队列里留下无法解析的
  悬挂 id（B21）。而"移除来源"在产品上只表示不再扫描这个文件夹。
- **选项**：① 删除曲目行；② 保留行并标记 `missing`，只删 `roots` 与 `scan_runs`；
  ③ 新增"来源状态"字段或来源状态表。
- **结论**：②。该根的曲目置 `missing = 1`、删 ledger 行、删根行三步放进**一个短事务**
  （局部 `BEGIN IMMEDIATE` / `COMMIT`，不抽通用事务层）：要么整个来源停止管理，要么什么都不变，
  不会留下"根仍注册、曲目却已全部 missing"的半截状态。v2 表结构完全够用：`missing` 表达"当前不可用"，
  `tracks.path` 唯一保证重新添加时按路径命中**同一行**，于是 id、`added_at`、收藏、歌单、覆盖、
  队列引用全部原样恢复；仍不存在的文件保持 `missing`。扫描进行中移除同一来源会被拒绝
  （`scanningRoots` 守卫），否则未结束的遍历会把它写回去。
- **被否方案**：① 与"不删除用户关联"直接矛盾；③ 为一个可以由 `missing` + 路径唯一表达的状态
  新增字段/表，属于给一个问题造一套框架。
- **后果**：移除后曲库不再显示这些曲目，但数据仍在；重复移除 / 添加幂等。
  代价是曲目行会一直留在库里（`root_id` 指向已删除的根），直到文件夹被加回来或被显式清理——
  这是有意的：删行等于删用户的收藏锚点。
